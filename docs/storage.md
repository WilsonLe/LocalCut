# Local storage and recovery

Opening createEditor explicitly creates IndexedDB localcut-v1 and OPFS localcut/. Model preparation uses localcut-asr-v1 in Cache Storage. Tests pass a separate namespace. All paths on a GitHub Pages origin share storage; cleanup must remain scoped to LocalCut resources.

Appearance uses the separate, versioned localStorage key `localcut.appearance.v1` containing `{ version: 1, preferences }`. It stores only enumerated UI choices, not credentials, media, project data or chat. Reading appearance at startup does not initialize editing storage. Root and `/LocalCut/` on the same origin share this preference. Storage events synchronize tabs; reset removes only this key. Unknown versions and invalid fields use safe defaults; read/write failures leave session customization usable and show an unsaved notice. Appearance is outside project backups and does not require a project-schema migration.

Workspace preferences use `localcut.workspace-preferences.v1` with `{ version: 1, preferences }`. The whitelist is `chatWidth`, `chatCollapsed`, `mediaOpen`, `exportFormat`, and `aiModel`; credentials, sharing consent, content and runtime state cannot be hydrated or saved through this owner. Reads precede rendering and do not initialize IndexedDB/OPFS or AI. Writes patch the latest saved record to preserve unrelated choices; storage events read the current record instead of replaying stale event payloads. Simultaneous writes remain last-writer-wins (localStorage offers no transaction across read/modify/write). Failed writes preserve session choices for retry and trigger an actionable toast. Finite widths are rounded/clamped to 280–560, booleans/enums and bounded model identifiers are validated, and malformed/unknown versions fall back to defaults. Same-origin root/Pages tabs share choices; removing this key resets workspace defaults in other tabs, and unrelated keys are ignored.

Workspace and appearance records remain separate so Appearance Reset removes only its existing key. Both are outside project snapshots, versions and JSON backups, with no project migration. Rollback to older code ignores the workspace key and preserves project storage. See the [preference audit](workspace.md#local-user-preferences) for inclusion/exclusion decisions.

IndexedDB contains projects, 100 undo/redo snapshots, lifetime idempotency receipts, metadata, transcripts, derivative records, and journals. A document/history/receipt change uses one atomic transaction with a revision check. Unsupported schemas and malformed imports fail without replacing a saved project.

Project records also contain an append-only `versions` array, separate from the bounded undo/redo stacks. Each entry has a stable ID, increasing number, creation timestamp, kind (`initial`, `autosave`, or `restore`), complete project snapshot, and optional `restoredFrom` version ID. Create/import initializes a baseline; opening a legacy record adds a baseline of its current normalized state without changing its edit revision or undo/redo history. This additive record extension does not change the IndexedDB database version. Existing versions are never normalized again or changed by edits.

The editor schedules a trailing one-second autosave after committed edits, undo/redo and project notifications. Saving uses an atomic transaction on the authoritative stored document and deduplicates its current revision. Switching projects, entering version browsing and disposing flush pending saves; opening recovers a working revision left by a tab closed before its timer. Edits are durable before the debounce, so a forced browser close cannot lose committed editing data. Multiple tabs can save the same revision without duplicate versions. Storage failures are reported; the working project remains intact and saving can be retried.

Restoration verifies the authored current revision and receipt content, preserves any pending current state as a version, then commits the selected historical state at the next edit revision and appends a `restore` version in the same document/history/receipt transaction. It is undoable; retrying the same request replays its receipt. Original files referenced only by historical versions remain retained. Project deletion removes its versions alongside its document; JSON backups continue to contain the current state only, so they do not transfer local version history.

Rollback to older application code retains the current project and media, but that older writer does not preserve the additive version field when committing edits. Export a current JSON backup and retain an origin-storage backup before such a rollback; do not run old writers against projects whose version history must be retained.

Original media is immutable OPFS content identified by asset ID. An import journal precedes file mutation. An asset becomes ready only after the file finishes; failure removes partial content. Relink accepts a missing original with matching metadata; it does not overwrite a ready source.

Imports commit ready metadata and their publication journal marker in one IndexedDB transaction. Transcripts likewise commit only after inference succeeds and their source bounds are validated. Cancellation aborts either transaction while it is pending. After a successful commit, a late cancellation cannot remove the original or transcript and the job returns the committed result. Export files and frame bitmaps have no such editing-data commit: cancellation before delivery removes the finished export or closes the bitmap before reporting CANCELLED. Delivered artifacts remain the caller's responsibility to dispose.

Exports and derivatives also journal their temporary files. Explicit engine opening recovers abandoned journals under Web Locks. An active job's lock prevents another tab from deleting its work. Completed ready originals survive recovery. File reads report MISSING_ASSET with a relinking path when needed.

Derivative records track size/access time. Cleanup uses an LRU budget of 512 MiB, reduced for available origin quota, and reserves estimated space before imports, derivative conversion, and exports. A quota failure cleans the partial output, evicts eligible owned derivatives, and retries once; active reader locks and originals remain protected. Active PCM readers pin their asset resources. Cache eviction never deletes originals, edits, or transcripts. Quota exceptions become QUOTA_EXCEEDED. The browser can still externally evict origin storage, so retain source backups.

Project deletion removes the document/history and its receipts. Original media is conservatively retained, including shared and historical sources; it is not automatically reclaimed. Explicit original garbage collection needs a later consumer-facing retention policy. Artifact disposal removes the owned export file. Model-cache clearing deletes only the namespaced inference cache.

Version-one JSON backup envelopes contain the project, referenced asset metadata, and referenced source transcripts, without media bytes. Retain originals separately. Import validates the complete envelope and restores all records in one transaction, assigning fresh project, asset, and transcript IDs to avoid replacing existing data. Restored metadata is marked missing until relinking succeeds. The restored project starts at revision zero; relink each remapped asset ID to its original file before media-dependent work. Legacy bare project documents can still be imported, but require metadata already present in the same namespace; source kinds, duration bounds, and transcript ownership are checked before the project is stored. Import journals mark successful file publication transactionally with asset metadata, so interrupted relinks cannot be mistaken for complete originals.

Persisted keyframes have stable IDs. When an older version-one document omits those IDs, parsing generates them deterministically from the clip ID, property, and timestamp. Reopening the same document or retrying a command does not generate different identities. Subsequent snapshots and backups include the normalized IDs; no schema-version change or destructive storage migration is required.

Stored project records carry `identityVersion: 1` outside the canonical project document. Reading an unmarked legacy record normalizes its current project and complete undo/redo history in one IndexedDB transaction. The original release's duplicateClip operation could copy caption cue IDs; migration preserves the first owner in chronological history (oldest undo, current, then future redo order) and deterministically remaps later owners by clip ID and old cue ID. Reordering tracks cannot exchange identities across history. Missing legacy keyframe IDs are normalized at the same time. This structural migration does not advance any editing revision or change visual/timing content. Unsupported records, same-clip duplicates, and IDs colliding with other object kinds abort without publishing a marker. Marked records stay strict and do not repeat the history migration on normal reads.

New backup envelopes also carry `identityVersion: 1`. Unmarked external backups and bare documents are strict by default; callers may explicitly opt into the same limited cue repair with `projects.importJSON(text, { repairLegacyIdentities: true })`. The option cannot relax validation for marked backups. Backups include editing data and references, not originals or receipt/history tables.

New receipts carry `contentVersion: 2` and canonical raw request JSON. Unversioned receipts are compared using the exact original version-one parser behavior, rather than today's defaulting or ID generation. Thus an identical successful old request still replays after upgrade and before stale-revision checks, while changed content and newly supplied nested IDs conflict. Receipt contents are never silently rewritten during migration; unknown receipt versions fail closed.

No application shell caching or offline navigation is installed. Cached inference can run without remote model/runtime hosts after reload as long as the static app itself remains available.
