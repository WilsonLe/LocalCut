# Playwright journeys that reuse the open app

Compatible stories now run as named-step journeys; incompatible fixtures retain their isolation. Nine combinations at both hosting bases move 38 original cases into 18 journeys, reducing normal discovery from 221 to 201 cases on the integrated resizing/routing base. The other 183 cases retain their existing owners, including workflows that already covered several stories. It records the [user's preference](user-preferences.md#delivery-and-validation) to reuse the app and existing tabs, minimize browser instances, and use parallel tabs when their work is independent.

## What already gets reused

[The normal runner](../scripts/test-browser.mjs) launches one owned stable-Chrome process and connects concurrent Playwright workers through the supported browser protocol. Ordinary `page` and `context` fixtures still create fresh isolated contexts for unrelated tests; compatible steps reuse the same tab within their journey. The resource policy bounds workers without creating one browser instance per worker. Separate invocations still own separate browsers, so batch compatible selections into one command. Discovery with `--list` starts no browser. Functional UI checks use reduced motion while explicit animation, resizing and modal-focus regressions retain full motion.

Some existing tests already cover a journey: [workspace edits and exports](../tests/browser/workspace.spec.ts), [commands](../tests/browser/workspace-commands.spec.ts), [timeline operations](../tests/browser/workspace-timeline.spec.ts), and [archive round trips](../tests/browser/workspace-transfer.spec.ts) each assert several user stories in one pass. Extend the matching journey when its fixture and state fit instead of opening another app just for one more assertion.

## Reuse secondary tabs and parallelize safely

- Keep the journey's primary tab. When synchronization needs another tab, reuse an existing task-owned secondary page or create one with `context.newPage()` and navigate it to the required app/project. Opening the same URL does not copy the first page's session state. Playwright's journey-owned fixture context closes its secondary pages on success or failure; custom contexts/pages require `finally` cleanup. Leave unrelated manually opened tabs alone.
- A paired-tab lane can reuse the same two pages for appearance, interface size, chat/media/export preferences and saved-credential removal propagation. Existing examples live in [appearance](../tests/browser/workspace-appearance.spec.ts), [size](../tests/browser/workspace-size.spec.ts), [local preferences](../tests/browser/workspace-local-preferences.spec.ts), and [saved connections](../tests/browser/workspace-ai.spec.ts). Reset each feature's owned state and finish its observers before advancing; disconnect runs last.
- Pages in one context share origin storage and broadcasts. Use them for intentional cross-tab stories. Serialize shared preference writes and project revisions, with explicit barriers or awaited observable state, unless the test deliberately exercises a race. Reuse paired pages for [version conflicts](../tests/browser/versions.spec.ts) or [index leases](../tests/browser/asset-index.spec.ts) only in their own controlled lane.
- Run independent reads/assertions across pages with `Promise.all`, as the interface-size journey does after each preference change. Concurrent editing/preview work needs separate task-owned project/storage namespaces where supported, or separate contexts in the same worker browser. Production workspace journeys that use the default namespace need context isolation; opening extra same-context tabs does not provide it. Keep each page's pointer/keyboard sequence ordered.
- Prefer one invocation selecting the related specs. This reuses the runner, server and shared browser but still uses fresh contexts for existing separate tests. The `@journey` tests implement same-tab reuse with named `test.step` phases and shared setup/cleanup. Do not share mutable pages across unrelated top-level tests or use a serial dependent chain to mask missing setup.
- Normal acceptance shares one browser across resource-bounded concurrent workers, reserving one slot per isolated context worker. `LOCALCUT_BROWSER_WORKERS` can narrow the pool; it does not merge contexts or guarantee one tab. Retain separate serial performance/transcription runs. See [resource scheduling](development.md#expand-verification-at-the-boundary).

## Keep these boundaries

Startup/inertness and install-manifest checks must run before editor storage, workers or saved credentials have been initialized. They can be first steps of a fresh journey, or keep an isolated fresh context; they cannot be tacked onto a warm app and still prove startup behavior. Preserve explicit `/` and `/LocalCut/` assertions when consolidating; use an isolated journey context per base, or a deliberate paired-base storage test, because the paths share an origin.

Storage denial/quota, corrupt records/archives, legacy migrations, recovery, provider failover/partial output, OAuth callback handling, superseded requests, atomic commits and deletion/lease races retain focused fixtures and barriers. They may reuse a worker browser, but do not inherit arbitrary successful-journey state. Engine API coverage is a separate contract from visible UI behavior; a UI pass does not justify removing engine assertions.

Keep [real transcription](../tests/browser/transcription.spec.ts), [performance](../tests/browser/performance.spec.ts) and [opt-in paid-provider acceptance](../tests/live/openrouter.spec.ts) separate and serial. Performance retains its disk-backed profile and runs without competing browser workloads. Transcription retains real preparation and fresh-worker offline replay. [Native Safari](development.md#expand-verification-at-the-boundary) remains a separate additional channel. No consolidation may replace actual native codecs/inference with mocks or suppress privacy, cleanup or persistence assertions.

## Validate the journeys

Inventory old assertions against journey steps before removing any test. List selectors without launching Chrome, then run the affected journeys against both current production builds. Profile comparable revisions with the same fixtures/channel/resource settings; report browser/context/page counts, wall time, peak resource use and failures rather than assuming fewer cases mean faster acceptance. Apply the [normal development gates](development.md#expand-verification-at-the-boundary) after test or scheduler code changes. Selection alone is not runtime evidence. Report actual results separately in [validation](validation.md).
