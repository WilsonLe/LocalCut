# Playwright journeys that reuse the open app

This is a consolidation plan for the existing browser stories, not an implemented test refactor or a measured speedup. It records the [user's preference](user-preferences.md#delivery-and-validation) to reuse the app and existing tabs, minimize browser instances, and use parallel tabs when their work is independent.

## What already gets reused

[The normal runner](../playwright.config.ts) uses installed stable Chrome, adaptive workers and `fullyParallel: true`. Playwright's browser fixture is shared within a worker; ordinary `page` and `context` fixtures create a fresh isolated context and page for each test. Multiple test cases therefore do not necessarily mean multiple simultaneous browser instances. Separate invocations and additional workers can start additional instances; combining compatible cases primarily saves context, navigation and app/project setup.

Some existing tests already cover a journey: [workspace edits and exports](../tests/browser/workspace.spec.ts), [commands](../tests/browser/workspace-commands.spec.ts), [timeline operations](../tests/browser/workspace-timeline.spec.ts), and [archive round trips](../tests/browser/workspace-transfer.spec.ts) each assert several user stories in one pass. Extend the matching journey when its fixture and state fit instead of opening another app just for one more assertion.

## Compatible story groups

Each row is a proposed bounded journey. Combine the compatible assertions from these specs, not their entire contents indiscriminately. Preserve every retained assertion and map it to a named step when implementing; failure, fresh-state and engine-only tests described below remain separate. Reload and project switching happen in the same tab when the story requires them.

## Reuse secondary tabs and parallelize safely

- Keep the journey's primary tab. When synchronization needs another tab, reuse an existing task-owned secondary page or create one with `context.newPage()` and navigate it to the required app/project. Opening the same URL does not copy the first page's session state. Close owned secondary pages in `finally`; leave unrelated manually opened tabs alone.
- A paired-tab lane can reuse the same two pages for appearance, interface size, chat/media/export preferences and saved-credential removal propagation. Existing examples live in [appearance](../tests/browser/workspace-appearance.spec.ts), [size](../tests/browser/workspace-size.spec.ts), [local preferences](../tests/browser/workspace-local-preferences.spec.ts), and [saved connections](../tests/browser/workspace-ai.spec.ts). Reset each feature's owned state and finish its observers before advancing; disconnect runs last.
- Pages in one context share origin storage and broadcasts. Use them for intentional cross-tab stories. Serialize shared preference writes and project revisions, with explicit barriers or awaited observable state, unless the test deliberately exercises a race. Reuse paired pages for [version conflicts](../tests/browser/versions.spec.ts) or [index leases](../tests/browser/asset-index.spec.ts) only in their own controlled lane.
- Run independent reads/assertions across pages with `Promise.all`. Concurrent editing/preview work needs separate task-owned project/storage namespaces where supported, or separate contexts in the same worker browser. Production workspace journeys that use the default namespace need context isolation; opening extra same-context tabs does not provide it. Keep each page's pointer/keyboard sequence ordered.
- Prefer one invocation selecting the related specs. This reuses the runner, server and worker browsers but still uses fresh contexts for existing separate tests. Actual same-tab reuse requires the proposed stories to become one test with named `test.step` phases and shared setup/cleanup. Do not share mutable pages across unrelated top-level tests or use a serial dependent chain to mask missing setup.
- Use the existing adaptive worker budget and profile before changing allocation. For deliberately minimal instance usage or serial diagnosis, the documented `LOCALCUT_BROWSER_WORKERS=1` override narrows the runner to one worker. That does not merge contexts or guarantee one tab. Additional independent journeys can share that worker browser in isolated contexts; retain separate performance/transcription runs. See [resource scheduling](development.md#expand-verification-at-the-boundary).

## Keep these boundaries

Startup/inertness and install-manifest checks must run before editor storage, workers or saved credentials have been initialized. They can be first steps of a fresh journey, or keep an isolated fresh context; they cannot be tacked onto a warm app and still prove startup behavior. Preserve explicit `/` and `/LocalCut/` assertions when consolidating; use an isolated journey context per base, or a deliberate paired-base storage test, because the paths share an origin.

Storage denial/quota, corrupt records/archives, legacy migrations, recovery, provider failover/partial output, OAuth callback handling, superseded requests, atomic commits and deletion/lease races retain focused fixtures and barriers. They may reuse a worker browser, but do not inherit arbitrary successful-journey state. Engine API coverage is a separate contract from visible UI behavior; a UI pass does not justify removing engine assertions.

Keep [real transcription](../tests/browser/transcription.spec.ts), [performance](../tests/browser/performance.spec.ts) and [opt-in paid-provider acceptance](../tests/live/openrouter.spec.ts) separate and serial. Performance retains its disk-backed profile and runs without competing browser workloads. Transcription retains real preparation and fresh-worker offline replay. [Native Safari](development.md#expand-verification-at-the-boundary) remains a separate additional channel. No consolidation may replace actual native codecs/inference with mocks or suppress privacy, cleanup or persistence assertions.

## Validate an implementation

Inventory old assertions against journey steps before removing any test. List selectors without launching Chrome, then run the affected journeys against both current production builds. Profile comparable revisions with the same fixtures/channel/resource settings; report browser/context/page counts, wall time, peak resource use and failures rather than assuming fewer cases mean faster acceptance. Apply the [normal development gates](development.md#expand-verification-at-the-boundary) after test or scheduler code changes. This documentation-only plan launches no browser and claims no executed runtime coverage.
